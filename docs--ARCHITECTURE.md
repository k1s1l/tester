# Архитектура

## Два уровня: Claude интерпретирует, Python решает

```
Telegram ──► aiogram handlers ──► SalesAssistant ──► ClaudeService (structured output, Pydantic)
                                        │                 └─ при сбое: fallback_parser (правила)
                                        ▼
                         catalog / inventory / orders  ──►  PostgreSQL
                                        │
                                        ▼
                     texts.py (факты из БД) + короткая фраза Claude ──► ответ клиенту
```

| Claude (`app/services/ai.py`) | Python |
|---|---|
| определяет намерение (`intent`), бренд, модель, размер, цвет, бюджет, назначение | ищет товары в каталоге (RapidFuzz), проверяет остатки |
| распознаёт кроссовки на фото + уверенность | сопоставляет распознанное с каталогом |
| пишет 1–2 дружелюбные фразы на украинском | формирует все цены, размеры, наличие, альтернативы, итог заказа |
| — | резервирует, списывает, создаёт заказ, проверяет права, считает суммы |

Гарантии:

- Ответ Claude — JSON по схеме (`output_config.format`, `client.beta.messages.parse`), затем повторная
  валидация Pydantic. Невалидный ответ, тайм-аут, 429/5xx, отказ модели (`stop_reason=refusal`) → `AIUnavailable`
  → правило-ориентированный парсер. SDK сам повторяет 408/409/429/5xx (`CLAUDE_MAX_RETRIES`).
- Фраза Claude отбрасывается, если в ней есть цены, «в наявності», скидки, доставка (`_FACT_PATTERNS`).
  Цены и наличие всегда рендерятся из БД (`texts.py`).
- Сообщения клиента передаются как данные в тегах `<customer_message>`; системный промпт запрещает менять роль,
  раскрывать инструкции, менять цены. Попытки → `off_topic` → шаблонный ответ. Claude не имеет доступа к БД,
  секретам и инструментам — даже «успешная» инъекция не может изменить заказ или остаток.
- Персональные данные: телефоны и e-mail маскируются до отправки в Claude; шаги «имя/контакт» вообще не
  проходят через Claude. История диалога ограничена (`HISTORY_MAX_MESSAGES`) и устаревает (`DIALOG_TTL_HOURS`).
- Фото: проверка заявленного размера и типа до загрузки, затем «магические байты» (JPEG/PNG/WEBP) и лимит
  `MAX_PHOTO_MB`. Фото помогает определить модель, но наличие — только из БД. Неуверенно (<0.6) — просим
  другое фото или название. Нет точного совпадения — «точного збігу в каталозі немає» + похожие.

## Схема базы данных

| Таблица | Назначение | Ключевые ограничения |
|---|---|---|
| `products` | бренд, модель, артикул, цвет, категория, теги, цена (грн), описание, активность, `is_demo` | `sku` UNIQUE, `price > 0` |
| `product_photos` | Telegram `file_id` или https-URL | FK → products CASCADE |
| `product_sizes` | размер, `quantity` (физически), `reserved` | UNIQUE(product, size), `quantity ≥ 0`, `reserved ≥ 0`, `reserved ≤ quantity` |
| `customers` | Telegram ID, username, имя, контакт | `telegram_id` UNIQUE |
| `orders` | номер (#1001…), снимок данных клиента, статус, сумма, `idempotency_key` | UNIQUE номер и ключ, CHECK статуса |
| `order_items` | **копия** бренда/модели/артикула/цвета/размера/цены на момент покупки | цены не зависят от будущих изменений каталога |
| `order_status_history` | кто и когда менял статус | |
| `stock_reservations` | резерв: заказ, размер, количество, статус, `expires_at` | частичный индекс по активным |
| `stock_movements` | журнал всех изменений склада (`reserve/release/expire/sale/return/adjust/initial`) с остатками «после» | только добавление |
| `notifications` | outbox сообщений Telegram: статус, попытки, `next_attempt_at`, `last_error` | частичный индекс по pending |
| `waitlist_requests` | «повідомити про надходження» | |
| `fsm_records` | состояние диалога/оформления (aiogram FSM) | переживает перезапуски |

## Склад: когда резервируем и когда списываем

```
                  клиент подтвердил            админ: Оплачено / Відправлено
 доступно ──────────────────────────► резерв ───────────────────────────────► продано (quantity−1)
   ▲                                    │                                         │
   │   отмена клиентом / отклонение /   │                                         │ отмена после оплаты
   └──────────── истёк резерв ◄─────────┘                                         │ (return)
   ▲                                                                              │
   └──────────────────────────────────────────────────────────────────────────────┘
```

- **Резерв** создаётся в момент подтверждения заказа клиентом (не раньше — просмотр и черновик не блокируют товар).
- Резерв живёт `RESERVATION_TTL_MINUTES` (24 ч); подтверждение админом продлевает до `CONFIRMED_RESERVATION_TTL_HOURS` (72 ч).
- **Списание** (`quantity` уменьшается) — только при «Оплачено» или «Відправлено» (наложенный платёж).
  Поэтому отменённый или неоплаченный заказ никогда не «съедает» товар: резерв возвращается.
- Фоновая задача каждые 30 с: истёкшие резервы → заказ `expired`, пары снова доступны, клиент и админ уведомлены.
- Конкурентность: резерв — один `UPDATE … SET reserved = reserved + 1 WHERE quantity − reserved ≥ 1 RETURNING`.
  PostgreSQL блокирует строку и перепроверяет условие, поэтому из двух одновременных покупателей последней пары
  успех получит ровно один (тест `test_concurrent_last_pair`, `test_many_concurrent_buyers_never_oversell`).
  CHECK-ограничения дополнительно не дают остаткам уйти в минус даже при ошибке в коде.
- Идемпотентность: каждый черновик заказа получает токен = `orders.idempotency_key` (UNIQUE). Повторное нажатие
  «Підтвердити» возвращает уже созданный заказ. Плюс `SimpleEventIsolation` обрабатывает апдейты одного
  пользователя последовательно.
- Всё создание заказа (клиент, заказ, позиции, резерв, история, уведомления) — одна транзакция: при любой ошибке
  не остаётся ни заказа, ни «висящего» резерва (тест `test_db_error_rolls_back_everything`).

## Статусы заказа

| Из | Возможные переходы |
|---|---|
| Очікує підтвердження (`pending`) | підтверджено, відхилено, скасовано, резерв минув |
| Підтверджено (`confirmed`) | оплачено, відправлено, скасовано, резерв минув |
| Оплачено (`paid`) | відправлено, скасовано (товар возвращается на склад) |
| Відправлено (`shipped`) | завершено |

Админ-кнопки показывают только допустимые переходы; сервер всё равно проверяет переход и права (`ADMIN_IDS`).
Клиент может отменить свой заказ до оплаты/отправки.

## Уведомления (outbox)

Сообщения администратору/клиенту записываются в `notifications` в той же транзакции, что и заказ. Затем
отправляются сразу и, при неудаче, фоновой задачей: экспоненциальная задержка 15 с → 1 ч, `RetryAfter`
учитывается, постоянные ошибки (бот заблокирован, неверный chat id) помечаются `failed` с причиной в
`last_error` и в логах. Заказ сохраняется независимо от доступности Telegram.

## Безопасность — чек-лист

| Требование | Реализация |
|---|---|
| Секреты | только переменные окружения; `.env` в `.gitignore`; `SecretStr`; фильтр логов маскирует токены, ключи, пароли в DSN, телефоны |
| Права администратора | `IsAdmin` на уровне роутера + повторная проверка в обработчиках статусов; кнопки админа от не-админа → отказ |
| Валидация | Pydantic для каталога/ответов ИИ; нормализация имени/телефона/e-mail; размеры; фото по магическим байтам |
| SQL-инъекции | только SQLAlchemy с параметрами; поиск `ILIKE` через bind-параметры |
| Флуд | `RATE_LIMIT_PER_MINUTE` на пользователя + лимит запросов к Claude в час |
| Повторное оформление | idempotency key + изоляция событий + лимит 3 ожидающих заказа на клиента |
| Атомарность склада | условные `UPDATE`, `SELECT … FOR UPDATE`, CHECK-ограничения, транзакции |
| Webhook | секретный заголовок `X-Telegram-Bot-Api-Secret-Token` (без него — 401) |
| CSV | защита от formula injection, BOM для Excel, предупреждение о персональных данных |
| Персональные данные | маскировка перед Claude, `/forget`, автоматическое обезличивание закрытых заказов через `DATA_RETENTION_DAYS`, удаление старых диалогов |
| Бэкапы | `scripts/backup_db.sh` (pg_dump + ротация), сервис `backup` в docker-compose, бэкапы Railway (см. DEPLOY.md) |
| Завершение работы | SIGTERM → остановка polling/webhook, фоновых задач, закрытие клиента Claude и пула БД |
| Миграции | advisory lock — два контейнера не применят миграции одновременно |

Ограничение: анти-флуд и лимит ИИ хранятся в памяти процесса — рассчитаны на один экземпляр бота
(`numReplicas: 1`). Для нескольких реплик их нужно перенести в Redis.
